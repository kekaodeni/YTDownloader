# Send to YTDownloader (development companion)

This first-party extension sends an explicitly selected HTTP(S) URL to the
Windows desktop app. It never reads Cookie values, page content or browsing
history, and never starts a download. The desktop app retains its existing
Cookie source, quality selector, Profiles and yt-dlp pipeline.

## Install / configure

1. Use a development portable build containing **YTDownloaderBridge.exe**.
2. Open **Toolbox → Browser extension**, choose your browser, and use
   **Start setup** in step 1. Registration and the frozen Bridge/IPC are checked;
   success means the local connection is ready, not that a browser is connected.
3. Follow step 2 and open that browser's folder shipped in the extracted ZIP:
   `BrowserExtensions/Chrome`, `BrowserExtensions/Edge`, or `BrowserExtensions/Firefox`.
   No Python, Node.js or extension build step is needed for a portable package. Copy the
   browser installation page address if needed; paste it into its address bar.
4. Chrome / Edge: enable Developer mode at `chrome://extensions` /
   `edge://extensions`, select **Load unpacked**, and select that browser's folder.
5. Firefox: open `about:debugging` → **This Firefox** → **Load Temporary Add-on**
   and choose `manifest.json`. This is a real temporary developer installation,
   removed on restart. Persistent release installations require Mozilla signing;
   this build has not been submitted to AMO or a browser store.
6. Follow step 3: open the extension on a public HTTP(S) page and send a link. The desktop
   connection indicator changes only after an actual browser-to-host exchange.

The desktop **Test connection** runs the frozen host's protocol and IPC test.
It does not prove that an extension is installed. A configured registration is
displayed as **waiting for browser connection**, never as connected by itself.
Browser activity expires after five minutes. Move the portable application?
Use **Repair connection** from its new location, then reload the unpacked extension
from its new folder in the browser. Repairing Native Messaging cannot change a
browser's saved extension load path. Confirm reloading in step 2, then send a
new link to verify. Previous AppData extension folders and user files are kept;
they are never deleted or overwritten during migration. Remove connection unregisters
only this application's association; extension folders are preserved.
Native Host manifests/configuration stay in AppData and HKCU. The extension body
is loaded from the portable directory, including when that directory is read-only.

## Identity and layout

- `shared/`: one popup, background behavior, URL validation and ten browser locales.
- `manifests/`: distinct Chromium MV3 service-worker manifests and Firefox MV3
  background-script manifest. Firefox minimum version is 140.
- `identity.json`: Chromium **public** keys stabilize developer IDs. It contains
  no signing private key. Chrome and Edge use distinct IDs and registrations.
- Store builds may have other IDs. Enter the installed ID in the desktop page
  before configuring; no wildcard origins are trusted.
- `templates/`: Native Host examples; the desktop generates absolute paths in
  the current user's application data directory, never in HKLM.

## Security / lifecycle

Native Messaging accepts UTF-8 JSON with a 32-bit little-endian length prefix
on Windows, maximum 32 KiB. Protocol 1 supports `ping`, `send_url`, and
`get_capabilities`, with a bounded request ID. Origins / Firefox IDs must match
the local registration. Stdout carries protocol bytes only. The host uses a
current-user Windows named pipe, no network listener, and launches only the
locally associated application with fixed argv; URLs never enter a shell.

The app owns one process lock per Windows user and data directory. Incoming
URLs are queued (maximum 16) until the existing parse lifecycle is idle.
Identical URLs are deduplicated for three seconds; request IDs are bounded too.
`delivered` means the desktop accepted a URL, not that parsing or download
succeeded. Existing downloads continue independently.

Validation rejects credentials, non-HTTP(S), control characters, reserved local
hostnames, dotless names and non-public literal IP addresses. Public DNS names
are left to the existing resolver and configured proxy: this boundary is not a
DNS-rebinding / redirect firewall. No website allowlist is imposed.

## Checks

```powershell
.venv\Scripts\python.exe -m pytest tests/test_browser_*.py
vendor\tools\deno\deno.exe run --allow-read browser-extension/tests/core.test.mjs
```

The manifests and ten locale files are generated by
`scripts/generate_browser_assets.py`; existing public identities are preserved.
For source development, run `scripts/build_browser_bridge.ps1` to build this
project's host at `build/browser-bridge/YTDownloaderBridge.exe`. The source app
uses that exact path by default and exposes a copyable build command if missing.
An explicit `YT_DOWNLOADER_BRIDGE_EXE` override remains available for developer
verification. A frozen app always uses the Bridge beside its own executable;
it never searches PATH or silently borrows another installation's host.
Portable builds need no Python installed. Advanced management is collapsed by
default; it contains IDs, repair, confirmed removal and diagnostic paths. The
title's **View installation guide** opens an independent local dialog; it keeps
the background browser selection and scroll position. Basic steps remain on
the main page. Source mode composes extensions beside the project's Bridge;
frozen installations never copy the full extension into AppData.

## Reference review

Architecture was reviewed against the official
[Chrome](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging),
[Edge](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/native-messaging)
and [Firefox](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging)
Native Messaging specifications. Firefox's origin argument and
`allowed_extensions` are handled separately from Chromium's origins.

Also reviewed: [imsyy/yt-dlp-gui](https://github.com/imsyy/yt-dlp-gui),
[dotcomaki/yt-dlp-gui](https://github.com/dotcomaki/yt-dlp-gui), and
[VittorioCodes/send-to-yt-dlp](https://github.com/VittorioCodes/send-to-yt-dlp).
Their architectures and privacy assumptions differ; no third-party extension
source code has been copied into this implementation. All three reference
repositories were confirmed to use the MIT license at the time of review.
