# YTDownloader v0.2.0 下载基准记录

测试日期：2026-09-02（Asia/Shanghai）

## 目的与控制变量

本次测试用于判断应用下载速度差异是否来自代理路径、应用包装层或分片并发。测试固定以下条件：

- URL：`https://www.youtube.com/watch?v=jNQXAC9IVRw`（19 秒公开短视频）
- 精确格式组合：`395+251`
- 协议：`https+https`
- yt-dlp：`2026.08.19`
- 相同的锁定 Deno、FFmpeg、系统网络策略和本机 VPN 状态
- 每个配置至少运行 3 次，使用中位数，运行次序交替

系统代理由每个新任务在运行时重新解析。报告只注明“系统代理”，不在源码或文档中固化本机端口。CLI TTFB 在首次完整运行后发现采集缺失，修正采集器后单独补跑 3 次。

## 结果

| 配置 | 成功次数 | 中位墙钟时间 | 中位吞吐量 | 中位 TTFB | 重试 / 分片错误 |
|---|---:|---:|---:|---:|---:|
| 参考 CLI 默认 | 3/3 | 5.235 s | 88.5 KiB/s | 4.625 s | 0 / 0 |
| 应用默认（自动=1） | 3/3 | 4.375 s | 105.9 KiB/s | 3.766 s | 0 / 0 |
| 应用并发 1 | 3/3 | 4.703 s | 98.5 KiB/s | 3.860 s | 0 / 0 |
| 应用并发 4 | 3/3 | 4.797 s | 96.6 KiB/s | 3.891 s | 0 / 0 |
| 应用并发 8 | 3/3 | 5.906 s | 78.4 KiB/s | 4.046 s | 0 / 0 |

有效下载文件均为 474,393 字节。两次完整测试、CLI 补测及诊断样本合计流量仍远低于 1 GB 上限。

## 结论

1. 在同一 URL、精确 format ID 和网络策略下，没有观察到应用包装层比参考 CLI 慢；因此现有证据不支持“应用未接入系统代理”。
2. 当前格式是普通 HTTPS 音视频流，不是可并行的分片协议。并发 4/8 没有带来收益，并发 8 反而更慢。
3. “应用默认”和“并发 1”使用相同有效并发值但仍有约 7% 的中位差异，说明短样本主要受解析、握手及瞬时网络波动影响，不能把小差异解释为确定的参数收益。
4. 根据“所有运行无错误，且选择处于最快中位吞吐量 5% 内的最低并发数”的规则，自动并发保持为 `1`。

这次测试不证明高并发对 HLS/DASH 分片永远无效。设置页仍提供 1、2、4、8 的显式选项；只有后续在相同控制变量下使用真正分片协议得到可重复收益，才应改变自动默认值。

```powershell
.\.venv\Scripts\python.exe scripts\benchmark_download.py --runs 3 --network-mode system
```
